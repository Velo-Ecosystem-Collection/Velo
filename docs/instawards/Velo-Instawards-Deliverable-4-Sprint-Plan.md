# D4 — Managed relayer integration and validation plan

## Decision

Proceed to D4 as a **validation and delivery sprint**. The managed Testnet custody and owner workflow are now implemented locally and documented in ADR-0005. D1–D3 code, the saved D2/D3 smoke reports, and reported development setup are useful inputs; none substitutes for a frozen-revision production Testnet run, two integrated dApps, 50 settled sponsored transactions, or the reviewer package. Keep D4 open until its evidence gates below pass.

Use ADR-0005's encrypted Convex custody as the primary path for newly provisioned projects. Preserve manually configured relayers for existing projects; never silently replace their account or move its funds. The managed implementation changes custody configuration and owner setup, while public Gas HTTP and SDK contracts stay compatible. Deploy and exercise every D4 path only on Stellar Testnet.

The deadline is **12 elapsed hours from kickoff**. This is a compressed delivery window against the SOW's 32-hour D4 allocation; it does not change that budget or waive any acceptance criterion. It is feasible only if the production keyring/backup, owner and reviewer access, three participants, funded Testnet accounts, and two runnable dApps are ready at kickoff or can be unblocked immediately. If a prerequisite remains blocked, report partial completion rather than lowering the agreed criteria.

## Managed relayer acceptance — added for ADR-0005

This section replaces the manual signer setup as the primary new-project path. It does not remove or migrate existing legacy relayers.

1. **Deployment custody configuration.** Development and production each use an independently generated versioned keyring, a stable exact `VELO_GAS_CUSTODY_DEPLOYMENT_ID`, and an explicitly controlled `VELO_GAS_MANAGED_RELAYER_PROVISIONING_ENABLED` flag. Never copy development encryption material into production. Confirm protected backup and recovery for every key version. Evidence may record deployment identity, configuration presence, active key version, and flag state; never include keyring values, plaintext keys, ciphertext, nonces, or authentication tags. Do not use `VELO_GAS_TESTNET_RELAYER_SIGNERS_JSON` as the managed-custody readiness check; it belongs to the legacy signer path.
2. **Provisioning.** On a project without an existing relayer, confirm project creation queues provisioning and the owner can retry a failed attempt. Confirm a public address appears only after encrypted custody is durably committed, only one custody record/address is accepted, and concurrent/restarted attempts do not publish a losing candidate. Confirm failure or missing configuration leaves the project usable, publishes no replacement address, and never stores plaintext. Verify decryption/context/address failures fail closed without legacy-signer fallback.
3. **Funding and balance.** On Testnet, verify the owner wallet flow uses `CreateAccount` for an absent relayer account and native XLM `Payment` for an existing account, with prepared intent and ledger result matching. Exercise **Get Testnet funds** through the fixed faucet, owner authorization, project-scoped 24-hour cooldown, and uncertain-response account recheck. Capture a fresh balance and spendable amount after reserves, liabilities, fee, and commitments; stale or unavailable data must not appear spendable. Never include signed XDR or secrets in the evidence.
4. **Activation and policy.** Link at least one active contract. Verify the review card shows 10 XLM/day, 100 requests per wallet per UTC hour, and the active linked contract set. An owner explicitly enables from the review card; the generic policy form cannot perform the initial managed activation. Verify editors retain policy-edit permissions, viewers remain read-only, and later limit/allowlist changes are stored by safe readback.
5. **Pause and recovery.** Verify owner pause/resume behavior and that the maintenance fence blocks new admission, policy enablement, and execution sends during withdrawal while reconciliation can continue. Exercise a proven-unsent cancellation separately from an uncertain submission; recover an uncertain withdrawal only with its pinned identity, never a replacement payment. Keep keyring versions and deployment identity configured. Rollback does not delete custody or evidence.
